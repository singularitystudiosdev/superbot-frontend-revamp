Start with a local-first single-file app: tasks, projects, and a week grid.

## What I'd build first

**Persistence and the data model come first**, because every view is just a projection of the same three records. Get that shape right and the rest is rendering.

1. **State + storage.** One `state` object, one `save()` that writes to `localStorage`. Everything else reads from it. This is the piece that decides whether the app survives a reload, so it goes in before any UI.
2. **Task capture and completion.** A composer, a checkbox, a delete. The loop you touch fifty times a day.
3. **Projects as a rollup.** Projects own tasks; the project row shows `done/total` and a progress bar. No separate project entity to keep in sync, just a filter over tasks.
4. **The week grid.** Seven day columns, each holding tasks whose `day` matches. This is the part that makes it a planner instead of a list.
5. **Load meters.** Sum the estimates per day against an 8h capacity. This is the one bold element: a thin bar under each day header that fills as you schedule. It is what tells you Tuesday is already full.
6. **Week navigation.** Prev, next, today. Cheap once the grid exists.

The data model is three fields deep:

```js
project = { id, name, color }
task    = { id, title, projectId, est, done, day }   // day = "YYYY-MM-DD" or null
```

`day === null` means backlog. That single nullable field is what lets one task list serve both the backlog and the planner, so you never duplicate a task between views.

Stack: one HTML file, no build step, no dependencies, no network. When you want it shared across the team, keep the exact state shape and swap the `localStorage` read/write for a small API (SQLite plus a thin server, or Supabase). The UI does not change.
